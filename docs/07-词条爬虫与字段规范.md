# 07 · 词条爬虫、字段规范与数据模型

> 配套工程：`crawler/`（详见 `crawler/README.md`）
> 本文记录：App 词条页数据模型的发现过程、字段字典的来源、爬虫的设计与已知边界。

---

## 7.1 一个关键的发现：App 的数据模型就在 APK 里

第一次爬出来的词条虽然释义正确，但缺少可数性、词源、句型、SYNONYMS 栏等
**学习型词典的核心语法标注**。追查这些字段的去向时，在
`assets/ciku/oxford_necdict.ui_resources.adgz` 里找到了一段内嵌 PHP：

```php
1/dictpage/index.php
  $viewParams['wordsData'] = '{ … 38632 字节的完整 JSON 样例 … }';
```

这是 **App 渲染词条页所用的完整数据模型**。解析后得到 239 条字段路径，
其结构如下（`tools/extract_wordsdata.py` 可复现）：

```
details.body[].dictionary.<dtype>
├── key / uwid / type / chaju(层级) / statistic / exampleUwid[]
└── body[]
    ├── head { word, pron[], pospron[], freq[], liebiao[] }   ← 考试标签
    ├── dict { key, word, uwid, chn, def, pos, symbol, aw }
    ├── sense[]
    │   ├── pos / ext / pron[] / addition{title,def,additionuwid}
    │   ├── subsense[]        ← 三级义项层级（a / b / c，■ / ◆）
    │   │   ├── def{trans,ex} / origin / symbol / pron[] / showtag
    │   │   └── example[] / addition{}
    │   └── beforesense{trans,ex}
    ├── derivative[] { word, uwid, pos, symbol, addt, ext, example[] }
    ├── origin / homo / phrase / phraverbs
    └── navigation[] { chn, def, dtype, type, uwid }
```

**结论**：App 的词条页是**服务端渲染 + 客户端本地词库**的混合结构。
模板里的字段名是权威规范，但**绝大多数字段只在服务端填充**。

## 7.2 逐项追查：哪些在本地，哪些不在

用这份模型当清单，回到 6 个本地词库里逐字段核对
（`tools/find_levels.py`、`tools/survey_fields.py`）：

| 模型字段 | 本地出处 | 结论 |
|---|---|---|
| `dictionary.<dtype>` | `dict.raw` 的 `dictionary` | ✅ 本地有 |
| `pron[]` / `pospron[]` | `dict.raw` / `bianxi.raw` 的 `pron` | ✅ 本地有（bianxi 带完整 `aw` 直链） |
| `sense[].def{trans,ex}` | `bianxi.raw` 的 `sense[]` | ✅ 本地有 |

| 词类标签（`<poscolor>`） | 同上 | ✅ |
| 词形标签（`<formcolor>`） | 同上 | ✅ |
| 交叉引用（`<em2>` / `<er subuwid>`） | 同上 | ✅ |
| 词形变化表 | `qiaoji.raw` 的 `transform` | ✅ |
| 同/反义词、搭配 | `qiaoji.raw` 的 `syn` / `opp` / `dapei` | ✅ |
| **词根分解** | `qiaoji.raw` 的 `associate` + `<mk>` 标记 | ✅ |
| 用法栏目（SYNONYMS/COLLOCATIONS…） | `bianxi.raw` 的 `unbox` / `h` | ✅ |
| 句型（pattern） | `bianxi.raw` 的 `pattern` | ✅ |
| 词族（und） | `bianxi.raw` 的 `und` | ✅ |

### 由此得出的重要判断

> **本 APK 里的「第10版」（dtype 17208）只是一块释义块**：
> `dictionary["17208"]` 仅含 `allchn` / `alldef` / `pos`。
> OALD10 完整的语法 apparatus（子义项 a/b/c、每义项的 pattern、SYNONYMS 栏、
> Origin 词源段落、CET 考试标签）**只存在于服务端**，未随包下发。

因此爬虫采用**双轨结构**：

- `definitions` / `edition_definition` / `senses[]` / `examples[]` / `phrases[]`
  → **严格按目标版本（17208）过滤**；
- `related.*`
  → **跨版本共享素材**（辨析库的用法栏目、巧记库的词形/词根/同反义），
  每条记录自带 `dtype` 字段标明来源版本。

这样既不丢数据，也不会把第9版的释义混进第10版。

## 7.5 词根分解的实现

`qiaoji.associate` 的结构：

```
associate.bar[]                     词根分组（bar[].name 是显示名，如「全部」）
  └─ combine[]                      按词根再分组
       ├─ key                       词根本身（如 "a" / "ban"）
       └─ list[]                    该词根下的词
            ├─ word                 带 <mk> 标记的词形，如 "<mk>ban</mk>dage"
            ├─ def / phon / pos / uwid
            └─ audio                完整音频直链
```

`split_mk()` 把 `<mk>` 标记还原成**去标记后的纯文本 + 词根偏移**：

```json
{"word": "bandage", "word_marked": "<mk>ban</mk>dage",
 "root": "ban", "root_spans": [{"root": "ban", "start": 0, "end": 3}],
 "def": "（用于包扎伤口或保护受伤部位的）绷带", "phon": "/ˈbændɪdʒ/",
 "pos": "noun", "uwid": "1191712498",
 "audio_url": "https://audio.haidii.com/audio/17001/b/72e3e5d5/814c3a0bf/bandage_gb_1.mp3"}
```

`root_spans` 用去标记后的字符偏移，前端可直接做彩色渲染（对应 App 里
`-er` + `abandon` 那种彩色分词）。

## 7.6 音频直链的可得性

直链格式：

```
https://audio.haidii.com/audio/{dtype}/{lang}/{const}/{itemHash}/{file}.mp3
```

- `{const}` 按词典版本固定（如 17001 → `72e3e5d5`）；
- `{itemHash}` **每个音频条目独有**。

验证结论：`{itemHash}` **无法本地推导**（试过 md5/sha1/crc32 对
name / word / uwid / parentWord 等组合，均不匹配）。

因此采用「反查」策略：把 `bianxi` / `qiaoji` / `ui_resources` 里出现的
**57,181 条**已知 URL 建成「mp5 文件名 → 完整 URL」索引
（`tools/build_audio_index.py`，缓存为 `work/data/audio_urls.*.json`），
爬取时按文件名命中就给出直链，否则 `audio_url: null` + `audio_url_known: false`。

覆盖率（抽样）：

| 库 | 不重复音频文件名 | 可还原 URL | 覆盖率 |
|---|---|---|---|
| `example.raw` | 526,720 | 15,142 | 2.9% |
| `dict.raw` | 246,355 | 24,419 | 9.9% |

`bianxi` 里的词条发音与内联例句**自带完整 `aw` 直链**（无需反查），
这部分是 100% 可用的。

## 7.7 爬虫设计

```
crawler/oald10/
├── config.py         版本元数据（dtype → 词典名/版次/封面）
├── extract.py        抽取主逻辑
├── labels.py         内联标记解析 + 标签字典加载
├── enums_check.py    编码值字典加载
├── validate.py       schema 校验 + 链表一致性 + 版本一致性
├── indexes.py        索引构建
├── state.py          断点续爬状态 / 原子写 / 追加流水
└── cli.py            命令行
```

### 索引文件

| 文件 | 内容 |
|---|---|
| `_index_by_key.json` | 主键索引：`key → {uwid, file, senses, examples, phrases, sha256, entry_type, frequency, cefr, oxford_3000/5000}` |
| `_index_by_uwid.json` | uwid → key（与 `def`/`example` 库的 uwid 对齐） |
| `_index_alphabet.json` | 字母序倒排：首字母 → `[key…]` |
| `_index_frequency.json` | 词频索引（`renqun` 降序） |
| `_index_stats.json` | 全量统计 + 错误清单 + 版本元信息 |
| `_manifest.jsonl` | 成功流水（追加写，含每词的 sha256） |
| `_errors.jsonl` | 失败流水（追加写） |

索引是 **O(n) 写出**，所以做了 **60 秒限流**（`INDEX_FLUSH_INTERVAL`），
避免每 200 词就重写一遍越来越大的索引文件。

### 断点续爬的四重保障

1. **词条文件即真相** —— `out/<dtype>/<safe(word)>.json` 存在且能解析、
   `_meta.ok == true` 即视为完成；即使状态/流水/索引全部丢失也不会重复爬。
2. **追加流水** —— `_manifest.jsonl` / `_errors.jsonl` append-only + `fsync`，
   崩溃最多丢最后一行。
3. **原子替换** —— 临时文件 + `os.replace()`，读者永远看不到半截 JSON；
   启动时自动清理 `.tmp_*`。
4. **索引增量累积** —— 索引 `load()` 已有内容继续累积，`flush()` 原子写出。

### 错误回避

| 风险 | 处理 |
|---|---|
| 单个词条异常 | 捕获 → `_errors.jsonl` → **不中断整体** |
| 词条不在本版本 | 正常跳过，**不计失败**（不污染错误日志） |
| 写盘中途崩溃 | 原子替换，不产生半截 JSON |
| 写完内容损坏 | 回读 + **schema 校验**，不过则删除并记失败 |
| 字段类型漂移 | schema 强制字符串化 ID 与受控枚举 |
| 本机路径泄露 | schema 显式禁止 `_meta.source.decoded_dir` |
| Ctrl-C | 捕获信号，先存状态与索引再退出 |

## 7.8 校验规则

`validate.py` 的检查项：

**Schema 层**（`jsonschema` draft 2020-12，`additionalProperties: false`）
- 必填字段齐全
- `uwid` / `parent_uwid` 为数字字符串
- `entry_type` / `lang` / `defdtype` / `dtype` 为受控值
- `senses[].defdtype` 与 `examples[].dtype` **必须等于目标版本**
- `audio_url_known` 与 `audio_url` 一致性
- `_meta.source` 不含 `decoded_dir`

**内置结构检查**（无 jsonschema 时降级使用）
- `prev` / `next` 不指向自身
- `links.derivatives` / `compounds_and_phrases` 的 `parent_uwid` 与本词一致
- `_meta.integrity.content_sha256` 为合法 SHA-256

实测：注入 uwid 非法、枚举越界、版本漂移、本机路径四类缺陷，
校验器全部捕获。

## 7.10 踩坑记录：Windows 保留设备名导致爬取卡死

### 现象

首次全量爬取在第 6,988 个词（`con`）处**永久卡死**：进程 CPU 仅 10%、
内存正常、无异常输出，文件数停在 6,987 不再增长。

### 定位

加了两层看门狗后拿到调用栈：

```
Timeout (0:00:40)!
  File "...\json\__init__.py", line 293 in load
  File "...\oald10\cli.py", line 69 in _is_done
  File "...\oald10\cli.py", line 257 in main
```

即卡在 `_is_done()` 里的 `json.load()`——**读文件**而不是解析逻辑。

### 根因

`safe_name()` 用 URL 百分号编码，字母数字原样保留，于是词 `con` 的文件名是
`con.json`。**Windows 把 `CON`/`PRN`/`AUX`/`NUL`/`COM1-9`/`LPT1-9`
当作保留设备名，即使带 `.json` 扩展名也照样解释为设备**：

- `os.path.exists("con.json")` → **True**（控制台设备存在）
- `open("con.json")` → 打开**控制台设备**
- `json.load(fp)` → 从 **stdin** 读 → **永久阻塞**

39,802 个候选词里恰好只有 `con` 一个命中。

### 修复

```python
_WINDOWS_RESERVED = (
    {"con", "prn", "aux", "nul"}
    | {f"com{i}" for i in range(1, 10)}
    | {f"lpt{i}" for i in range(1, 10)}
)

def safe_name(word: str) -> str:
    enc = urllib.parse.quote(word, safe="")
    ...
    stem = enc.split(".", 1)[0].lower()
    if stem in _WINDOWS_RESERVED or enc.lower() in _WINDOWS_RESERVED:
        enc += "_w"          # con → con_w
    return enc
```

回归测试见 `tests/test_crawler.py::test_safe_name_escapes_windows_reserved_names`。

> 这个坑很隐蔽：进程不报错、不退出、只是「慢」，很容易误判成是词库读取慢
> 或内存不足。定位靠的是 `faulthandler` 的周期性栈转储。

## 7.11 去重与「全量保留」

### 7.11.1 去重检查发现的问题

第一次全量爬完后做去重检查，结论与预期相反：**不是有重复，而是去重过头了**。

| 词库 | 记录数 | 唯一 key | 重复 key | 多余记录 |
|---|---|---|---|---|
| `dict` | 288,469 | 228,902 | 29,332 | 59,567 |
| `def` | 694,281 | 694,281 | 0 | 0 |
| `example` | 444,861 | 444,658 | 175 | 203 |
| `bianxi` | 31,523 | 31,008 | 506 | 515 |
| `qiaoji` | 21,178 | 15,679 | 3,570 | 5,499 |
| `archetype` / `index` | 48,719 / 13,211 | 同 | 0 | 0 |

**同一个词在 `dict.raw` 里会有多条记录**（不同 uwid = 不同义项组）。
例如 `a` 有 **16 条**记录：11 条只带 `17001`（第9版），5 条带
`17203`/`17208`/`21135` 等。原实现用 `lookup()` 只取第一条 →
- 漏掉了 4,225 个词的其余义项组
- 合计 **4,828 条释义条目与例句被丢弃**
- `a` 只有 1 条释义（实际 19 条）、`run` 只有 ~35 条（实际 50 条）

`bianxi` / `qiaoji` 也有重复 key，原实现同样只取第一条，会丢掉用法栏目与词形变化。

### 7.11.2 改为「全量保留」

**不再按版本过滤**，所有内容全部保留，每条自带版本标记：

| 字段 | 内容 |
|---|---|
| `entries[]` | 该词在 `dict.raw` 的**全部**记录（= 全部义项组），每条带自己的 `definitions`（各版本释义块）、`pronunciations`、`images`、`prev`/`next`、`frequency`、`cefr`、`oxford_3000/5000` |
| `entry_uwids[]` | 全部义项组的 uwid |
| `definitions{}` | 按**所有版本**合并的释义（`chn` / `def` / `pos`） |
| `edition_definition` | 目标版本（第10版）的速查视图 |
| `senses[]` | **全部版本**的释义条目，每条带 `defdtype` |
| `examples[]` | **全部版本**的例句，每条带 `dtype` |
| `phrases[]` | **全部版本**的短语/搭配/习语，每条带 `defdtype` |
| `related.bianxi[]` | 该词的**全部**辨析/用法栏目记录 |
| `related.qiaoji` | 合并后的词形变化、词根分解、同/反义词、搭配、拼读 |
| `related.archetype[]` | 派生词形（**不限条数**，全保留） |
| `related.sugg[]` | 联想词组（按 uwid 反查，418,264 条反向索引） |
| `related.shards[]` | 词库分片（按 uwid 反查，153,908 条反向索引） |
| `related.pinyin` | 拼音双向映射 |
| `related.image_marks[]` | 插图标注 |
| `stats.by_edition` | 各词典版本下的条目数 |

schema 升到 `oxford-dict.crawl/3`。

### 7.11.3 覆盖率校验：查出第三个丢失点

只查「输出有没有重复」是不够的——真正要问的是**「漏了多少」**。
于是加了 `tools/coverage_check.py`：从源库直接算出每个抽样词
「应有多少条 entries / senses / examples / bianxi / qiaoji」，
再与输出文件逐项比对。

结果立刻暴露出第三个丢失点：

> **`example.raw` 的索引 key 混用两种**：一部分是**例句文本**
> （如 `$10,000 was debited from their account`），一部分是 **uwid**
> （如 `1192231653`）。按 uwid 二分查找会漏掉一部分例句。

| 词 | 源库应有 | 修复前 | 修复后 |
|---|---|---|---|
| attention | 61 | 52 | 61 |
| arouse | 17 | 11 | 17 |
| tincture | 5 | 1 | 5 |
| grubber | 3 | 0 | 3 |

修法：全表扫一遍 `example.raw` 建 **uwid → 索引项** 映射
（44.4 万条，8.3 秒，带磁盘缓存 `example.uwid_index.json`）。

**最终校验**：随机抽样 120 个词条，
「源库应含 entries=176 / senses=1614 / examples=970 / bianxi=55 / qiaoji=44」
与输出 **0 不一致**。

### 7.11.4 本轮修掉的三个真实 bug

| # | 问题 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | Windows 保留设备名 | 爬取在第 6,988 个词永久卡死 | `con.json` 被当成控制台设备，`open()` 后 `json.load` 从 stdin 读 | `safe_name()` 对 `con/prn/aux/nul/com1-9/lpt1-9` 加 `_w` 后缀 |
